# Migrating from 0.5 to 0.6

This guide lists the changes since 0.5.0 that can break a build or change
runtime behavior.

## Compile errors

- A `pgComposite` field that is an array of arrays (`seq[seq[T]]`,
  `seq[PgArray[T]]`, `seq[array[N, T]]`, or an `Option` element of any of
  these) no longer compiles. 0.5.0 wrote such a field as a Nim repr, which
  the server rejected. Use a `PgArray[T]` field for more dimensions.
- A `pgComposite` field that is an `Option` inside another `Option` or
  inside a `PgArray` (`PgArray[Option[T]]`) no longer compiles. 0.5.0 wrote
  a Nim repr (`some(1)`). A `seq[Option[T]]` or `PgArray[T]` element already
  holds NULL.

## Behavior changes

- The `toPgParam` that `pgComposite` declares now encodes every field by its
  Nim type instead of the `$` visible where `pgComposite` was called. A
  `seq[T]` or `array[N, T]` field (one dimension), a `PgArray[T]` field (any
  dimension), a `PgHstore` field and a `seq[byte]` or `array[N, byte]`
  (bytea) field write their PostgreSQL literals: 0.5.0 wrote a Nim repr,
  such as `@[1, 2]`, which the server rejected, and a distinct type without
  a `$` did not compile. A
  `seq[Option[T]]` field keeps its NULL elements. A `distinct` field is
  written as its base type, so a custom `$` on it, as on a domain field, is
  no longer called. A `distinct` over a type with no PostgreSQL counterpart,
  such as `Lsn` over `uint64`, is still written through its own `$`.
- `getComposite` now reads enum, domain (`distinct`), uuid, numeric, money,
  interval, time/timetz, bit, inet/cidr, MAC, XML, text-search, geometric,
  hstore, `JsonNode`, range and multirange fields, `seq[T]`, `array[N, T]`,
  `PgArray[T]` and `set[T]` fields, and `seq[byte]`/`array[N, byte]`
  (bytea) fields too, in text format; a
  binary read supports the same except ranges/multiranges and money, which
  need text format (a binary money value does not carry its scale). 0.5.0
  read numbers, `bool`, `string` and `DateTime` only and raised
  `PgTypeError` for the rest.
- A `set[T]` field is written as a 1-D array of quoted members
  (`{"1","2"}`), which the server reads as the same value as 0.5.0's
  `{1, 2}`, and is now read back from one too.
- A `PgMoney` field is read with scale 2, so another `lc_monetary`
  fractional-digit count raises. Writing one uses the value's scale and the
  server rounds it to its `lc_monetary` fractional digits. The written text
  has `.` as its decimal point, so an `lc_monetary` whose decimal point is
  `,` misreads it.
- An object field outside the library's types is still written through its
  own `$`, verbatim (`times.Time`'s drops the fraction of a second; use
  `DateTime`). An object or tuple field with only std's generic `$`, such as
  a nested composite, raises `PgTypeError` instead of sending a Nim repr.
  That includes an unnamed tuple such as `(int32, int32)`, whose `(1, 2)`
  0.5.0 sent and a composite attribute accepted; build the nested composite
  in SQL instead.
- A domain field is decoded by the base type of the Nim `distinct` type: the
  Nim base must match the domain's base, which a binary read cannot verify
  (the domain OID is dynamic).
- The 1-D array getters (`getIntArray`, `getStrArrayElemOpt` and the rest)
  and `parseTextArray` accept the `[l:u]=` prefix the server prints in text
  format for a lower bound other than 1, and drop the bound, as the binary
  read already did. 0.5.0 raised `PgTypeError`. A prefix whose count does
  not match the elements still raises.
- A malformed text `box[]` literal now raises `Invalid array literal`
  instead of `Invalid box array literal`.
