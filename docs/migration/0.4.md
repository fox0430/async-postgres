# Migrating from 0.3 to 0.4

0.4.0 tightens the public contract, moves several defaults to libpq's, and
fixes data bugs. This guide lists the changes since 0.3.0 that can break a
build or change runtime behavior; fixes that only turn a wrong result into
the right one are summarized at the end.

## Most likely to bite

- `parseDsn` and `initConnConfig` default `sslmode` to `prefer`, and
  `verify-ca`/`verify-full` require `sslrootcert`
  ([Connections](#connections-tls-and-dsns)).
- `initConnConfig` gained `hostaddr` right after `port`: positional calls
  that pass the user and stop at or before the database still compile but
  fill the wrong fields ([Connections](#connections-tls-and-dsns)).
- `DateTime` values are written and read in UTC
  ([Values](#values-that-change-without-an-error)), and sessions start with
  `TimeZone=UTC` whatever the server, database or role sets, so `timestamptz`
  text prints `+00`, and `now()::date`, `date_trunc` on `timestamptz` and
  `timestamp` columns filled by `DEFAULT now()` follow UTC unless the DSN or
  `extraParams` sets `TimeZone` (`DEFAULT` keeps the server's, database's or
  role's zone) ([Connections](#connections-tls-and-dsns)).
- Replication, logical and physical, no longer advances the slot by itself
  ([Replication](#replication)).
- `return`, or a `break`/`continue` that leaves the body, inside
  `pool.withConnection` and the other scoped blocks no longer compiles
  ([Compile errors](#compile-errors)).
- `PgTimeoutError` is now a `PgConnectionError`, socket failures raise
  `PgUnavailableError` instead of the backend's `OSError`, `TransportError`
  or `AsyncStreamError`, and a pool acquire whose connect fails raises
  `PgPoolError` ([Errors](#errors)).

## Upgrading in short

1. Update dependencies: the chronos backend needs chronos >= 4.4.0 and
   nim-bearssl >= 0.2.11 ([Build](#build)).
2. Fix the compile errors ([Compile errors](#compile-errors)).
3. Decide on TLS: 0.4 defaults to `sslmode=prefer` (0.3: disabled); add
   `sslmode=disable` to keep plaintext
   ([Connections, TLS and DSNs](#connections-tls-and-dsns)).
4. Decide on the session zone: sessions start in UTC, and
   `TimeZone=DEFAULT` keeps the server's, database's or role's zone as 0.3
   did ([Connections, TLS and DSNs](#connections-tls-and-dsns)).
5. Keep replication moving: call `confirmFlushed` once a change is durably
   processed, or pass `autoConfirm = true` to a pgoutput stream
   ([Replication](#replication)).
6. Review `except` clauses: `PgTimeoutError` is a `PgConnectionError` now,
   and a pool acquire whose connect fails raises `PgPoolError`
   ([Errors](#errors)).

## Build

- The chronos backend needs chronos >= 4.4.0 (checked at compile time) and
  nim-bearssl >= 0.2.11 (not checked; 0.2.9 and older fail to compile
  `pg_bearssl.nim`).

## Compile errors

- **Import `async_postgres`.** The hub re-exports a reviewed public surface
  instead of every submodule wholesale. Internals 0.3 leaked through it are
  no longer re-exported, among them `pg_auth` (SCRAM/MD5), the statement
  cache helpers (`conn.clearStmtCache`, `addStmtCache`, ...), `cellInfo`,
  `parseAffectedRows`, `colTypeOid`, the DSN sub-parsers (`parseUriDsn`,
  `parseSslMode`, `applyParam`, ...; use `parseDsn` or set the fields),
  `newPgQueryError`, the wire and codec helpers (`sendMsg`, `nextMessage`,
  `encodeInt32`, `decodeInt32`, `decodeBinary*`, `bytesToString`,
  `pgCopyBinaryHeader`/`pgCopyBinaryTrailer` (use
  `addCopyBinaryHeader`/`addCopyBinaryTrailer`), `pgArrayElemOid`,
  `pgArrayArrayOid`, ...), `PipelineOp`/`PipelineOpKind`,
  `configureKeepalive`, `rollbackGrace`/`rollbackGraceMs` and
  `nameAccessor`/`optAccessor`. `pgEpochOffset` is gone; use `pgEpochUnix`,
  which has the same value.
  Supported imports are `async_postgres` and the hub modules it lists
  (`async_postgres/pg_pool`, ...); deeper submodules such as
  `async_postgres/pg_connection/types` are unsupported. Only what
  `async_postgres` re-exports is covered: a hub module imported directly
  still reaches some of the names above (`async_postgres/pg_protocol` has
  `encodeInt32`), with no compatibility promise.
- **Range flags.** `rangeHasLower`, `rangeHasUpper`, `rangeLowerInc` and
  `rangeUpperInc` are replaced by PostgreSQL's `rangeLbInc`, `rangeUbInc`,
  `rangeLbInf` and `rangeUbInf`. The bits mean different things (0x02 was
  "has lower", now "lower inclusive"; a bound is present when the range is
  not empty (`rangeEmpty`) and its `*Inf` flag is clear), so remap the logic,
  not just the names.
- **Private fields.** `PgMoney`, `PgBit`, `LargeObject`, `PreparedStatement`
  and `Cursor` fields are read-only accessors now (`m.amount`, `bit.nbits`,
  `stmt.fields`, ...). Build values with `initPgMoney`, `initPgBit` or
  `parseBitString` instead of object literals; `LargeObject`,
  `PreparedStatement` and `Cursor` come only from `loOpen`, `prepare` and
  `openCursor`. `PreparedStatement` is a `ref object` now, so copying the
  handle shares the server-side statement instead of snapshotting it.
  `UpdateMessage.hasOldTuple` is a proc derived from the new
  `keyKind` field (`'K'`, `'O'` or `'\0'`); set `keyKind` in literals.
- **`PgConnection`** keeps read-only `state`, `txStatus`, `pid`, `host`,
  `port`, `config`, `createdAt`, `sslEnabled`, `serverParams` and
  `notifyDropped`, and setters for `notifyMaxQueue`,
  `listenReconnectMaxAttempts`, `listenReconnectMaxBackoff` and
  `stmtCacheCapacity`. Set callbacks with `onNotify`, `onNotice`,
  `onReconnect` and `onNotifyOverflow` (0.3 fields `notifyCallback`,
  `noticeCallback`, `reconnectCallback` and `notifyOverflowCallback`), and
  `tracer` in `ConnConfig` before connecting (`conn.tracer` is gone; read
  `conn.config.tracer`). `listenErrorMsg` is now `listenError`
  (`ref PgListenError`). The transport, buffers, statement cache,
  `secretKey`, `serverCertDer`, `heldSessionLocks`, the listen internals
  (`notifyQueue`, `listenChannels`, `startListening`, `reconnectInPlace`)
  and the other bookkeeping fields are no longer reachable. Drop calls to
  `clearStmtCache`: the statement cache clears itself when `DISCARD ALL` or
  `DEALLOCATE ALL` runs on the connection, so run `DEALLOCATE ALL` where you
  cleared it by hand. A `DEALLOCATE ALL` inside a function or `DO` block
  (`DISCARD ALL` is refused there) reports no such tag; the next cache-hit
  Bind then fails once with `26000`, and the cache clears itself. `query`,
  `exec` and `queryEach` re-issue that Bind-phase failure once from Parse
  transparently (see [Pool](#pool)); otherwise — `queryDirect` /
  `execDirect`, pipelines, inside a transaction, or a `26000` raised after
  `BindComplete` — the `26000` still surfaces. A pipeline sends every op
  before the first reply, so `executeIsolated` reports a `26000` for each
  cache hit in the batch, not just the first. A cached
  statement broken by DDL fails once with `0A000` and is dropped (0.3 kept
  failing until `clearStmtCache`).
- **No escaping scoped blocks.** `return`, or a `break`/`continue` that leaves
  the body, is rejected in `withConnection`, `withPipeline`,
  `withReadConnection`/`withWriteConnection`, `withCursor`, `withLargeObject`
  and `withAdvisoryLock`/`withAdvisoryLockShared`. `withTransaction*` and
  `withSavepoint*` already rejected `return`; they now reject an escaping
  `break`/`continue` too (0.3 let it skip COMMIT or RELEASE). Assign inside
  the block and return after it:

  ```nim
  var n: int64
  pool.withConnection(conn):
    n = await conn.queryValue(int64, "SELECT count(*) FROM t")
  return n
  ```
- **Callback types.** `CopyOutCallback` takes `data: sink seq[byte]`: add
  `sink` to hand-written callbacks or build them with `makeCopyOutCallback`.
  On asyncdispatch `RowCallback` is `{.raises: [CatchableError].}`, as on
  chronos, so a `queryEach` callback that can raise `Exception` no longer
  compiles: a proc variable without `raises`, or a bare `raise` (any on Nim
  before 2.2.8; later, one under `except:` or `except Exception:`). Re-raise
  with `except X as e: raise e`.
- **`raises` lists.** Several parameter encoders (`toPgParam` and
  `toPgBinaryParam` for `string`, `seq[byte]`, `DateTime`, `PgMoney`, ...,
  and `toPgParam(PgUuid)`), `initPgBit`, `formatPgMoney`, `isNull` and
  `initConnConfig` can raise, row accessors can raise `PgProtocolError`
  besides `PgTypeError`, and APIs whose error type changed
  ([Errors](#errors)) raise the new one (`parseLsn`: `PgTypeError`, was
  `ValueError`); callers with a `raises` list must allow it.
  Adding `PgError` absorbs these changes except for `getNumeric*`,
  `getIntArray*`, `getInt64Array` and `parsePgNumeric`, which now raise
  `CatchableError`, and `parseDsn`, which adds `ValueError`.
- **money.** `formatPgMoney` takes `thousandsSep: string` (was `char`) and
  gains `sepBySpace` and `groupDigits`. Prefer `initPgMoneyConventions` with
  the `conv` overloads of `formatPgMoney`/`parsePgMoney`/`getMoney*`.
- **`pgEnum`/`pgDomain`.** `pgEnum` requires an enum type and `pgDomain` a
  distinct type. When the second argument (`pgDomain(T, Base)`) is itself a
  distinct type, `T` must be declared from it (`T = distinct Base`); 0.3
  accepted any two distinct types over the same base. If redeclaring `T`
  breaks its `{.borrow.}` procs, pass the plain underlying type instead
  (`pgDomain(T, string, oid)`).
- **`startReplication`** and **`startPhysicalReplication`** gained
  `statusInterval` before `callback`, and `initPoolConfig` gained
  `resetQueryTimeout` before `pipelined`; pass the later arguments by name.
  `connectToHost` takes a `HostEntry` instead of a host and a port.
- **`pool.exec(sql, @[])`** and `pool.query(sql, @[])` are ambiguous now that
  `seq[PgParamInline]` overloads exist (as `conn.exec` and `conn.query`
  already were); omit the empty list.
- `BackendMessageKind` gained `bmkNegotiateProtocolVersion`, so an
  exhaustive `case` over it needs the new branch.
- `ProtocolError` is renamed to `PgProtocolError`; the old name is a
  deprecated alias (a warning only).

## Connections, TLS and DSNs

- **`initConnConfig` parameter order.** `hostaddr` now follows `port`;
  `sslCert`, `sslKey` and `sslSni` follow `sslRootCert`; `loadBalanceHosts`
  follows `targetSessionAttrs`. `initConnConfig("h", 5432, "alice", "pw",
  "db")` still compiles but sets `hostaddr = "alice"` and shifts the rest,
  and so does a call that stops at the user or password (one that goes on to
  `sslMode` positionally no longer compiles); pass everything after `port`
  by name.

  ```nim
  # 0.3: positional user, password, database
  initConnConfig("db.example.com", 5432, "alice", "secret", "app")

  # 0.4: everything after port by name ("alice" would be hostaddr positionally)
  initConnConfig(
    "db.example.com", 5432,
    user = "alice", password = "secret", database = "app",
  )
  ```
- **TLS by default.** `parseDsn` and `initConnConfig` default `sslmode` to
  `prefer` (was `disable`): TLS is used whenever the server offers it, and a
  server that refuses it gets a plaintext connection and a warning on
  stderr. A failed TLS handshake does not fall back to plaintext, so a server
  whose TLS the backend cannot speak (chronos is TLS 1.2 only; asyncdispatch
  needs 1.2 or later) fails to connect by default. On asyncdispatch built
  without `-d:ssl`, `prefer` silently stays in plaintext. Add
  `sslmode=disable` to keep 0.3 behavior.
- **SNI.** On asyncdispatch, TLS connections send SNI under every `sslmode`
  (0.3: `verify-full` only), except to an IP-literal host. Set `sslsni=0`
  (`sslSni = false`) for a server or proxy that rejects or misroutes on it.
  chronos still sends SNI under `verify-full` only, where BearSSL checks the
  same name, so `sslsni` changes nothing there.
- **`ConnConfig(...)` object literals** still mean `sslDisable`; they also
  mean `sslSni = false`, so asyncdispatch sends no SNI even under
  `verify-full` (0.3 did). A literal needs `host` (or `hostaddr`) and
  `port`: `connect` raises `PgConfigError` for a missing one (0.3 dialed
  port 5432 when `port` was left out). Prefer `initConnConfig`.
- **SCRAM-SHA-256-PLUS** is chosen whenever TLS is up and the server offers
  it, now also under `require_auth=scram-sha-256` and on asyncdispatch (0.3
  never used it there). Behind a TLS-terminating proxy, add
  `channel_binding=disable`. A server that offers it over a plaintext client
  connection (a proxy that adds TLS only towards the server) now fails with
  `PgSecurityError`, even with `channel_binding=disable`; 0.3 fell back to
  SCRAM-SHA-256.
- **Authentication exchange order.** An out-of-order request — a
  cleartext/MD5 method switch, `AuthenticationSASL` after a password
  request, or a SASL reply before its request — is refused with
  `PgSecurityError` (0.3 answered a method switch). `onInsecureAuth` and
  `onDeprecatedAuth` fire only for a request the client answers, so a
  request refused by `require_auth` or `channel_binding` no longer calls
  them.
- **`verify-ca`/`verify-full` need `sslrootcert`.** 0.3 fell back to the system
  or bundled trust store; in 0.4 `connect` raises `PgConfigError` for a TCP
  host. `newPool` raises it as is while opening its `minSize` connections;
  a later acquire that needs a new connection fails with `pekConfigFault`
  ([Pool](#pool)). `sslrootcert=system` is not supported: point it at a CA
  bundle file. On asyncdispatch,
  `verify-full` now also checks the host name and IP SAN. On chronos,
  `verify-full` to an IP-literal host always fails with `PgSecurityError`
  (BearSSL cannot match IP SANs); use a host name.
- **`hostaddr`** is no longer an alias of `host`: it is the address dialed,
  while `host` names the server for TLS. Beside a `hostaddr`, a `127.0.0.1`
  host (the default `initConnConfig(hostaddr = ...)` leaves, or an explicit
  one) is not a name to verify, so `verify-full` with only a `hostaddr`
  fails `connect` with `PgSecurityError`; set `host` to the name in the
  certificate. A Unix-socket directory in `hostaddr`
  (`hostaddr=/var/run/postgresql`), which 0.3 dialed like `host`, raises
  `PgConfigError`; move it to `host`.
- **`hosts` wins.** `parseDsn` now fills `hosts` for keyword/value DSNs too
  (0.3: URIs only), and `connect` dials `hosts` and copies its first entry
  over `host`, `hostaddr` and `port`. Assigning `cfg.host`, `cfg.hostaddr`
  or `cfg.port` after `parseDsn` is ignored; edit `cfg.hosts` instead.
- **Every address is dialed.** A host name is dialed address by address in
  the resolver's order, IPv6 included (0.3: IPv4 only on asyncdispatch, the
  first address only on chronos). An error reply from the address that
  accepts does not move on to the next, so `localhost` reaching `::1` needs
  a pg_hba line for `::1`; add `hostaddr=127.0.0.1` to keep 0.3's address.
- **`target_session_attrs=primary`/`standby`/`prefer-standby`** follow the
  server's recovery state (`in_hot_standby`, else `pg_is_in_recovery()`), as
  libpq does; 0.3 used `transaction_read_only`.
- **Pinned session parameters.** Startup always sends `client_encoding=UTF8`
  and an ISO `DateStyle` (0.3 sent neither), overriding server, database and
  role settings, including a database's or role's DateStyle field order (the
  server's configured order still applies). Another encoding or a non-ISO
  output style in the DSN, `options` or `extraParams` raises
  `PgConfigError`, `client_encoding=auto` and `DateStyle=DEFAULT` included;
  a later `SET` to either closes the connection with `PgProtocolError`. Set
  the field order in the DSN (`DateStyle=DMY`).
- **`TimeZone` is UTC.** Startup also sends `TimeZone=UTC` (0.3 sent none),
  overriding server, database and role settings, so that `DateTime`
  parameters bound to `timestamptz` keep their instant.
- **Server-side SQL follows UTC.** `timestamptz` text prints `+00`
  (`simpleQuery`, `getStr` on a text column, `::text`, `to_json`), and so do
  `CURRENT_DATE`, `now()::date`, `date_trunc`, `to_char` and `extract` on
  `timestamptz`, and `timestamp` columns filled by `DEFAULT now()`, whose
  rows from clients in the server's zone then differ by its offset.
- **Setting another zone.** Unlike `client_encoding` and `DateStyle` above,
  any zone may be set in the DSN (`TimeZone=Asia/Tokyo`), `options`
  (`-c TimeZone=Asia/Tokyo`) or `extraParams`; `TimeZone=DEFAULT` as the
  DSN's `TimeZone` or an `extraParams` entry keeps the server's, database's
  or role's zone, as 0.3 did by sending none, while `-c TimeZone=DEFAULT` in
  `options` reaches the server and fails the connect. In a zone other than
  UTC, `DateTime` parameters bound to `timestamptz` shift by its offset
  unless sent as `timestamptz` (`toPgTimestampTzParam`,
  `toPgBinaryTimestampTzParam`, `toPgTimestampTzArrayParam`).
- **A dropped startup value fails `connect`.** When a UTC session reports
  another zone, as behind a pooler that drops startup parameters (PgBouncer
  passes it on), `connect` fails with `PgConnectionError`: set
  `TimeZone=DEFAULT`, or make UTC the server's, database's or role's zone
  (`Etc/UTC`, `GMT` and the other UTC aliases count). A later `SET TimeZone`
  is allowed; the pool undoes it on release ([Pool](#pool)).
- **DSN parsing** follows libpq and the WHATWG URL rules:
  - URI: the authority ends at the first `/` or `?`. Percent-encode `/` and
    `?` in the user or password (`%2F`/`%3F`) and `@` in the database
    (`%40`); a raw `@` in a query needs a path (`host:5432/?user=a@b`). 0.3
    accepted a raw `/` in the user or password and a raw `@` in a path-less
    query (`host:5432?user=a@b`), and misread a raw `@` in the database
    (`u:p@h/d@b` dialed host `b`); 0.4 rejects all three.
  - URI: `+` is a literal plus (0.3 decoded it as a space, passwords
    included); a `%` not followed by two hex digits raises (write `%25`).
  - URI: an empty `[]`, anything after `]` other than `:port`, and an
    unbracketed IPv6 address (`postgresql://::1/db`) raise; 0.3 accepted
    them.
  - URI: hosts and ports are percent-decoded (0.3 used them verbatim), so
    `%2Fvar%2Frun` names a Unix-socket directory and a zone id is written
    `[fe80::1%25eth0]`.
  - URI: `host`, `hostaddr` and `port` in the query take effect; a query
    `host` replaces the hosts in the authority, whose ports then apply to it
    as in libpq. 0.3 ignored all three and dialed the authority's hosts and
    ports, or 127.0.0.1:5432 for an empty authority, so
    `postgresql:///db?host=/var/run/postgresql` went over TCP.
  - URI: a query item without `=` raises (0.3 skipped it), and so does one
    with an empty key (0.3 put it in the startup packet, which the server
    rejected).
  - Keyword/value: a backslash escapes the next character, quoted or not.
    Write Windows paths with `/` or doubled backslashes.
  - Integer values (`port`, `connect_timeout`, ...) reject digit-group
    underscores (`5_432`).
  - An empty host (`host=''`, `postgresql://:5433/db`, `h1,,h2`,
    `initConnConfig(host = "")`) raises unless a `hostaddr` is given for it;
    an omitted one still means 127.0.0.1.
- **Connect timeouts.** `connectTimeout` applies to each resolved address, not
  the whole attempt. With several hosts a timeout is folded into the
  `PgConnectionError` aggregate; a single host still raises
  `AsyncTimeoutError`. A non-positive `connect_timeout` means no timeout
  (0.3: a negative one timed out at once).
- **SCRAM** iteration counts below 4096 are refused with `PgSecurityError`.
  The upper limit moves from 600,000 to `max_scram_iterations`
  (`maxScramIterations`; 10,000,000 by default).
- **`cancel()`** sends the CancelRequest over TLS when the session uses it
  (0.3: always in plaintext), waits for the server to hang up, and raises
  `PgTimeoutError` after `connectTimeout` or 10 s, whichever is longer. A
  failed dial or write raises a `PgConnectionError`, mostly
  `PgUnavailableError` (0.3: the backend's own error).

## Values that change without an error

- **`DateTime` is UTC.** `toPgParam(DateTime)`, `toPgDateParam`, text
  `tsrange`/`daterange` and multirange parameters (their arrays included)
  and `pgComposite` fields send the UTC wall clock and calendar day; 0.3 sent
  the value's own wall clock. Text-format reads of `timestamp`,
  `timestamptz` and `date`, their arrays and range bounds return UTC
  `DateTime`s, as binary reads already did; 0.3 used the local zone, so a
  column could read local on a query's first execution and UTC from the
  second on. For a
  `DateTime` not in UTC, such as a local one on a host not running in UTC:
  - a local `now()` written to a `timestamp` column is stored shifted by the
    offset;
  - `toPgParam(DateTime)` (and `sql` interpolation) sends a `timestamp`, which
    the server converts with the session `TimeZone` when the column is
    `timestamptz`. Sessions start in UTC, so the instant is right; with
    `TimeZone` set to another zone it is off by that zone's offset (0.3 was
    right when the session zone matched the client's);
  - `toPgDateParam` sends the UTC date, which differs from the local one for
    part of each day: east of UTC a date built at local midnight
    (`dateTime(2024, mJan, 1)`) is always sent as the day before, and west
    of UTC a value late in the day (from 19:00 in New York in winter) is
    sent as the next day;
  - `timestamp` reads keep the stored wall clock but are tagged UTC instead of
    local, and `date` reads are UTC midnight; `timestamptz` reads are the
    same instant in UTC (`.local` for display).

  Converting with `dt.utc` changes nothing, since 0.4 converts anyway. Build
  `timestamp`/`date` values in UTC (`dateTime(2024, mJan, 1, zone = utc())`),
  or use `timestamptz` with `toPgTimestampTzParam`.
- **`PgMoney` comparison.** `==`, `<`, `<=` and `hash` compare the decimal
  value across scales: `initPgMoney(100, 2) == initPgMoney(1000, 3)` is now
  true (0.3: false, and `<`/`<=` raised on mismatched scales).
- **Binary ranges.** 0.3 used wrong flag bits, so range and multirange
  columns read in binary (from a query's second execution on the same
  connection, or with `rfBinary`) came back with dropped or misplaced bounds
  and flipped inclusivity, and binary range and multirange parameters were
  malformed (the server rejected most with 08P01 and stored some with the
  wrong bounds). Both now match the server.

## Errors

| Situation | 0.3 | 0.4 |
|---|---|---|
| Bad DSN | `PgError` | `PgConfigError` |
| Bad `ConnConfig` | a Defect or `PgConnectionError` at connect (an out-of-range port wrapped around) | `PgConfigError` from `connect`; `parseDsn`, `initConnConfig` and `validateConnConfig` catch part of it earlier |
| Bad pool setting | `ValueError` from `initPoolConfig` only | `ValueError` from `initPoolConfig`, `newPool` and `newPoolCluster`; every negative duration (`fallbackTimeout` included) and a negative `maxPipelineSize` are now rejected too |
| Malformed or out-of-range value (encode/decode) | `PgTypeError` on most paths; `ValueError` (arrays, ranges, bytea, geometry, composites, `parseLsn`, ...), `RangeDefect` or `IndexDefect` on others | `PgTypeError` |
| Column index out of range | `IndexDefect` | `PgTypeError` |
| NUL byte in SQL text or a statement name | `ValueError` | `PgTypeError` |
| Socket read/write failure | the backend's own: `OSError` (asyncdispatch), `TransportError`/`AsyncStreamError` (chronos); a reset or EOF was already `PgConnectionError` | `PgUnavailableError` (a `PgConnectionError`), cause in `parent` when there is one |
| Timeout | `PgTimeoutError` (a `PgError`) | `PgTimeoutError`, now a `PgConnectionError`; a single-host `connect` timeout is still `AsyncTimeoutError`, not a `PgError` ([Connect timeouts](#connections-tls-and-dsns)) |
| Connection busy, used after your own `close()`, or a replication call outside a stream | `PgConnectionError` | `PgStateError` |
| Pool acquire whose connect fails | the connect error | `PgPoolError` (`kind`: `pekConnectFailed`, `pekRefused`, `pekConfigFault`, or `pekAcquireTimeout` if `acquireTimeout` ran out), cause in `parent` |
| Pool closed while waiting | `PgError` | `PgPoolError` (`pekClosed`) |
| COMMIT answered with ROLLBACK in `withTransaction*` (the body swallowed a query error) | silent success | `PgQueryError` 25P02, cause in `parent` when known |

What makes a `ConnConfig` bad: contradicting options, an unreadable cert, key
or CA, a port outside 1–65535, or a keepalive past `int32` or, on Linux, past
the kernel's limit (32767 s, 127 probes).

- `PgConfigError`, `PgStateError` and `PgTypeError` are `PgError`s but neither
  `PgConnectionError`s nor `ValueError`s. `except PgConnectionError` no longer
  catches config faults raised by `connect`, misuse, a stopped listener
  ([LISTEN/NOTIFY](#listennotify)) or a pool acquire's connect failures (now
  `PgPoolError`, cause in `parent`; the connects `newPool` makes for
  `minSize` still raise the connect error), and now catches `PgTimeoutError`
  and a multi-host `connect` timeout, folded into the aggregate (a pool's
  acquire timeout stays `PgPoolError`): put `except PgTimeoutError` first
  where you tell them apart.

  ```nim
  try:
    discard await pool.query(sql"SELECT 1")
  except PgTimeoutError:
    # a PgConnectionError now: catch it before its parent
    echo "timed out"
  except PgPoolError as e:
    # a pool acquire failed; e.kind says how (pekAcquireTimeout, ...)
    echo "pool: ", e.kind
  except PgConnectionError:
    # the connection is gone: reconnect
    echo "connection lost"
  ```
- `PgSecurityError`, `PgUnavailableError`, `PgProtocolError` and
  `PgListenError` are `PgConnectionError`s, `PgListenStoppedError` a
  `PgStateError`, `PgPoolError` a `PgError` but not a `PgConnectionError`,
  and `PgMessageTooLargeError` a `PgTypeError`; `except PgError` catches
  them all.
- `PgPoolError.kind` (`PoolErrorKind`) is new; besides the kinds above it
  has `pekQueueFull`, `pekBatchFailed`, `pekDefectWrapped` and `pekUnknown`.
- Catch `PgError` (or the specific type) instead of relying on Defects.
  Preconditions raise `ValueError`, which `except PgError` does not catch:
  pool settings and replication options as before, and now large-object
  arguments (0.3 returned no data for a negative length or a non-positive
  read chunk size, looped or raised `RangeDefect` on a non-positive write
  chunk size, and let the server reject a bad whence) and a NUL in
  `quoteIdentifier` (checked up front) or the new `quoteLiteral`.
- To recover from an error inside a transaction, use `withSavepoint`.

## Stricter input

These used to be accepted or silently misread, and now raise:

- Garbage in text-format values: integers (`12abc`, `1_000`), floats,
  booleans (`tx`), intervals, arrays (`{1,2,}`, or a multi-dimensional array
  read into a `seq`: read it as `PgArray[T]` with `getArrayND`, which needs
  `rfBinary`; a multi-dimensional `timestamp`, `timestamptz` or `date` array
  has no reader, so cast it to text), ranges, composites, money
  (`$1,23.45`).
- `'infinity'` and `'-infinity'` in `timestamp`, `timestamptz` and `date`
  values, range bounds, arrays and multiranges included (`PgTypeError`); 0.3
  already raised `PgTypeError` for text ones but misread binary ones (from a
  query's second execution) or raised `OverflowDefect`. Read such columns as
  strings instead (`col::text`, or `rfText` with `getStr`); no format decodes
  them into `DateTime`.
- Enum labels that match the Nim enum only after case or underscore folding
  (`in_progress` into `inProgress`): `getEnum*` now needs the label to equal
  `$value` (`PgTypeError`; 0.3 used `parseEnum` and raised `ValueError` for
  an unknown label). Give such values the label as their string
  (`inProgress = "in_progress"`).
- Mismatched wire OIDs (e.g. `getFloat` on a binary `int8`; array accessors
  check the element OID too, so `getIntArray` on a binary `float4[]` raises
  instead of decoding the bits as int32), and `getStr` on a
  binary uuid, timestamp, interval, json, jsonb, xml, ... column (0.3
  returned the wire bytes, which for json and xml was the text; bool,
  integer, float and numeric columns are still rendered as text, and types
  `rfAuto` never reads in binary, such as `oid`, still come back as wire
  bytes under `rfBinary`): use the typed accessor or `rfText`. Under the
  default `rfAuto`, `query`/`exec` results switch to binary once the same
  SQL text has already run on the connection (an earlier `exec` counts);
  `openCursor` and prepared statements stay in text.
- `getComposite` on a composite with more fields than the object (0.3
  ignored the extras, so readers now break after `ALTER TYPE ... ADD
  ATTRIBUTE`), and, in binary (`rfBinary`; `rfAuto` reads composites as
  text), a field whose type does not match the Nim field exactly (`int64`
  takes only `int8`; `string` takes only `text`, `varchar`, `bpchar`, `name`
  and `char`, not enum, json or uuid attributes, of which 0.3 read enum and
  json ones). Read such composites in text (`rfAuto` or `rfText`).
- `PgMoney` parameters whose scale differs from the `scale` argument of
  `toPgParam`, `toPgParamInline` or `toPgBinaryParam` (default 2, also used
  by `sql` interpolation and `seq[PgMoney]`); 0.3 sent the raw amount
  whatever the scale. For a locale with other fraction digits (JPY: 0), pass
  `scale` (`sql` cannot: bind `toPgParam(m, scale = 0)` with `query` or
  `exec`), or use `toPgMoneyArrayParam` for arrays.
- Out-of-range `timetz` offsets (on encode, `PgTypeError` replaces the
  server's `PgQueryError`); invalid `PgTime` and `PgTimeTz` fields on encode
  (0.3 sent them: binary `00:75` was stored as `01:15:00`).
- `openCursor` with a non-positive `chunkSize`; `prepare` with an empty name or
  one starting with `_sc_` (the statement cache's prefix). Both raise
  `PgTypeError`.
- `copyIn*` with a statement other than `COPY ... FROM STDIN`, and `copyOut*`
  with one other than `COPY ... TO STDOUT` (`PgQueryError`; a statement
  other than COPY has already run, so its effects stay, while a
  `COPY ... FROM STDIN` given to `copyOut` is aborted; 0.3 returned without
  an error, and hung on the latter).
- A top-level `withTransaction*` (Retry/Deadline variants included),
  `execInTransaction` or `queryInTransaction` on a connection already in a
  transaction (`PgStateError`; 0.3's inner COMMIT committed the outer work).
  Nest with `withSavepoint`.
- Transaction-level advisory locks (`advisory*Xact*`,
  `withAdvisoryLockXact*`) outside a transaction (`PgStateError`; 0.3
  released the lock at once).
- Concurrent `fetchNext`/`close` on one cursor (`PgStateError`).
- A `sqlParams` placeholder followed directly by `-` or `#` (`?-1`, `?#1`):
  it is left as the `?-`/`?#` operator, so the server rejects the statement
  or its parameter count. Write `? - 1` or `? # 1`.

## Behavior changes

### Pool

- With `pipelined = true`, `maxWaiters` also caps the queue of pending
  `pool.exec`/`pool.query` operations (`pekQueueFull` when full; with
  `maxWaiters = 0` every pipelined operation is rejected), and their finite
  `timeout` argument includes time spent queued.
- `acquireTimeout` bounds the whole acquire, health-check pings and connects
  included.
- A startup refused with 28P01 (password), 3D000 (database) or 42501
  (privilege), by every host when there are several, fails that acquire,
  and waiters nothing else can serve, with `pekRefused`; replenishment backs
  off to `connectBackoffMax` (unless `connectBackoffInitial` is 0). Later
  acquires still dial, so a server-side fix is picked up.
  `pool.connectRefusal` holds the cause.
- A connect that raises `PgConfigError` stops the pool dialing for good: an
  acquire that finds no idle connection waits for a borrowed one to come
  back, and fails with `pekConfigFault` once none is borrowed. Fix the
  config and create a new pool.
- `resetSession` statements are bounded by `resetQueryTimeout` (5 s default
  from `initPoolConfig`; a `PoolConfig(...)` literal leaves it unbounded).
- A `resetQuery` that leaves prepared statements in place (`RESET ALL`)
  keeps the statement cache; 0.3 cleared it on every release and left the
  statements on the server. A top-level `DISCARD ALL` or `DEALLOCATE ALL`
  still clears it. A `resetQuery` that drops them only inside a function
  (`SELECT app.reset_session()` running `DEALLOCATE ALL`) leaves the cache
  stale after every release, so the next cache-hit Bind fails with `26000`
  and drops the cache. Outside a transaction, `query`, `exec` and
  `queryEach` re-issue that op once from Parse (Bind failed before Execute,
  so nothing ran twice). Inside one (`withTransaction` included), the
  `26000` aborts the transaction and reaches the caller, as it does in
  `queryDirect` / `execDirect` and in a pipeline (`executeIsolated` reports
  it for each cache hit in the batch). Append a top-level
  `DEALLOCATE ALL` to such a `resetQuery`
  (`SELECT app.reset_session(); DEALLOCATE ALL`) so those paths do not fail,
  as 0.3's unconditional clear ensured.
- A `TimeZone` changed with `SET` is not passed to the next borrower:
  `resetSession` (run by the `with*` blocks, the pool's query and exec
  helpers and `resetSessionAndRelease`) sets back the zone the session
  started with, and `release(h)` and `release(conn)`, which skip it, discard
  the connection, as for a held advisory lock. Under `TimeZone=DEFAULT` it
  issues `RESET TimeZone`, so a zone changed by a server config reload is
  kept. A `resetQuery` that moves the zone, such as `DISCARD ALL` behind
  PgBouncer, costs one more round trip per release.
- A `Defect` raised in a pooled `with*` body surfaces as
  `PgPoolError(pekDefectWrapped)` with the Defect in `parent`, so
  `except CatchableError` now catches it. On chronos this covers a Defect
  raised in the body itself; one raised in an async proc the body awaits
  still escapes the event loop.
- `PgPoolCluster`'s `fallbackTimeout` also bounds the replica acquire, so
  reads fail over to the primary after it rather than after the replica's
  `acquireTimeout`.

### Transactions

- `withSavepoint` and `withSavepointDeadline` quote the name with
  `quoteIdentifier`. Raw SQL in the body that names a savepoint with
  uppercase letters (`ROLLBACK TO SAVEPOINT MySp`) no longer finds it; quote
  it there too, or use a lowercase name.
- A `Defect` raised in the body of `conn.withTransactionDeadline`,
  `withTransactionRetryDeadline` or `withSavepointDeadline` surfaces as a
  `PgError` with the Defect in `parent`, so `except CatchableError` catches
  it. On chronos, as in the pool, only a Defect raised in the body itself.
- Cancelling (chronos) a connection-level `withTransaction*` or
  `withSavepoint*` no longer attempts a ROLLBACK (0.3 rolled back when the
  cancel landed between round trips). A cancel that lands during a round
  trip closes the connection; one that lands between round trips (the body
  awaiting something else) leaves it open inside the transaction or
  savepoint, so roll back or close it yourself. A pooled connection is
  discarded on release.

### Advisory locks

- `withAdvisoryLock` and `withAdvisoryLockShared` no longer raise an unlock
  failure, even after a body that succeeded: it goes to the tracer's
  `onAdvisoryUnlockFailed`, as does an unlock that finds the lock not held.
  Their `timeout` now bounds the unlock too.

### LISTEN/NOTIFY

- The auto-reconnect stops at the first redial refused with 28P01, 3D000 or
  42501, or failing on config, instead of retrying up to
  `listenReconnectMaxAttempts`.
- `waitNotification` raises `PgStateError` when no listen pump is running
  and nothing is queued, and fails a call already waiting when `unlisten`
  or `stopListening` stops the pump (0.3 waited in both cases). When the
  pump died but the connection is still up it raises
  `PgListenStoppedError`, a `PgStateError` (0.3 waited here too), so a
  reconnect loop on `except PgConnectionError` misses it.
- `notifyMaxQueue <= 0` means no count limit (0.3: pull queue disabled). The
  new `notifyMaxQueueBytes` (16 MiB default) also caps the queue by size,
  whatever `notifyMaxQueue` is, and drops a notification larger than it
  unless a `waitNotification` call is already waiting for it. A push-only
  consumer that set 0 to skip buffering can set 1, but each arrival it
  never pulls then counts as an overflow (`onNotifyOverflow`,
  `notifyDropped`).

### Replication

- **The slot no longer advances by itself.** Keepalive and `statusInterval`
  replies report the flush position confirmed with `confirmFlushed(lsn)`, not
  the last one received. Call `confirmFlushed` once a change is durably
  processed, or pass `autoConfirm = true` to `startReplication` (pgoutput) to
  confirm each transaction after its callback. Without either (or a
  `sendStandbyStatus` of your own), `confirmed_flush_lsn` stays at the start
  position, WAL accumulates and a restart replays from there. On a logical
  stream confirm `CommitMessage.endLsn` or a keepalive's `walEnd`, never
  `receivedEndLsn` as 0.3's example did. `startPhysicalReplication` must
  call `confirmFlushed` too: otherwise a slot's `restart_lsn` stays put. A
  stream that never confirms also holds up the primary's commits (under
  `synchronous_commit` `on` or `remote_apply`) when it is a synchronous
  standby, or a logical consumer listed in `synchronous_standby_names`.

  ```nim
  # pgoutput: confirm each transaction after its callback returns
  await conn.startReplication(
    slotName,
    options = @{"proto_version": "1", "publication_names": "my_pub"},
    callback = onMessage,
    autoConfirm = true,
  )

  # or confirm explicitly once a change is durably processed
  discard conn.confirmFlushed(commit.endLsn)
  ```
- `startReplication` quotes option values itself: pass them unquoted. A
  value wrapped in quotes raises `ValueError` (`'my_pub'`, as 0.3 needed),
  except double quotes in `publication_names`, which keep a name's case
  (`"MyPub"`; unquoted, `MyPub` names `mypub`). A `proto_version` other than `1`
  raises `ValueError` (the bundled pgoutput decoder reads v1 only); it is
  added when omitted and `publication_names` is given. An empty option key,
  an empty `proto_version` or `publication_names`, and a negative `timeline`
  for `startPhysicalReplication` raise `ValueError` up front (0.3 sent the
  empty ones to the server and dropped a negative timeline), and so do a
  non-identifier key and a NUL in a value, which 0.3 rejected only after
  leaving the connection busy.
- A stream the server ends without CopyDone or an error (in practice a second
  logical `START_REPLICATION` on a connection that already streamed) closes
  the connection and raises `PgUnavailableError` (0.3 returned normally).
- A callback that raises marks the connection closed (0.3 left it stuck in
  replication mode), but its walsender holds the slot until you `close()`
  it: close it before resuming on another connection.
- `stopReplication` sends a final status with the confirmed position before
  CopyDone (0.3 sent CopyDone at once). Called from another task while the
  callback runs, it returns once the stop is queued: await
  `startReplication` rather than calling `close()` right after, or the stop
  may never go out.
- `readReplicationSlot` on a missing slot raises `PgConnectionError` (0.3
  returned `0/0`).

### Messages

- Client-side DSN and value-decoding errors no longer echo the value
  (passwords included) or cell contents; they report lengths and offsets.
  Certificate file paths are still named, and server error messages pass
  through as sent. Update log matchers that relied on the old text.
- `PgQueryError.severity` is the non-localized severity (`ERROR`, `FATAL`)
  when the server sends it (PostgreSQL 9.6+); 0.3 used the one that follows
  `lc_messages`.

## Fixes that change results

Code that worked around these 0.3 bugs should drop the workaround:

- `seq[byte]` (bytea) parameters are sent in binary; 0.3 sent the raw bytes
  as bytea text input.
- Binary `date` parameters before 1970 (`toPgBinaryDateParam`,
  `toPgDateArrayParam`) were sent a day late unless at UTC midnight.
- Text `time`/`timetz` `24:00:00`, text timestamps with a one- to
  five-digit fraction (`2024-01-01 12:00:00.5`), and text dates and
  timestamps with ` BC`, a year past 9999 or a UTC offset with seconds
  (`+09:18:59`, printed for historical dates in many zones) raised; they
  parse now.
- Intervals in text under a non-default `IntervalStyle` were misread
  (`sql_standard`) or sent the decoder into an endless loop (`iso_8601`,
  `postgres_verbose`); every style is read now.
- A cached statement re-run with other result formats returned corrupted
  values or raised `PgTypeError`, binary cursor rows were decoded as text,
  and `queryInTransaction` with `rfBinary` decoded the binary rows as text.
- `queryValue`, `queryValueOpt` and `queryValueOrDefault` returning a
  `string` (untyped, typed as `string`, or with a `string` default) and
  `queryColumn` returned the wire bytes of a binary column such as
  `timestamptz` or `uuid` from a SQL text's second execution on; they always
  read text now.
- `queryDirect`/`execDirect` evaluated each argument expression several
  times; each is evaluated once now.
- Binary `tsquery` swapped operands and dropped parentheses under `!`; it now
  decodes to the server's text form.
- bytea text in the escape format was returned verbatim; it is decoded now.
- A NULL `Option[PgUuid]`/`Option[PgMacAddr]`/`Option[PgMacAddr8]` binary
  parameter raised, and a NULL `Option[DateTime]` hit an `AssertionDefect`;
  both send NULL now.
- SCRAM passwords go through SASLprep, so passwords it changes (non-ASCII
  spaces such as U+00A0, characters mapped to nothing, non-NFKC forms)
  authenticate.
- SCRAM-SHA-256-PLUS binds with the hash of the server certificate (DER),
  hashed by the algorithm its signature names; 0.3 always used SHA-256, so a
  certificate whose signature is SHA-384 or SHA-512 (RSA-PSS included)
  failed authentication unless `channel_binding=disable`.
- Large objects with an OID of 2^31 or more raised `RangeDefect`.
- Text `PgHstore` parameters (`toPgParam`, `seq[PgHstore]`) are sent
  untyped, so `INSERT ... VALUES ($1)` into an `hstore` column needs no
  cast.
- `sql` and `sqlParams` leave placeholders inside SQL comments alone, and
  `sqlParams` no longer takes the `?` of `?-`, `?-|` or `?#` for one (a
  placeholder right before `-` or `#` now needs a space:
  [Stricter input](#stricter-input)).
