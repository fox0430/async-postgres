# Migrating from 0.4 to 0.5

This guide lists the changes since 0.4.1 that can break a build or change
runtime behavior.

## Compile errors

- `pgParams(v)` and `sql"…{v}…"` resolve `toPgParam` at the call site, as a
  direct `toPgParam(v)` call there does (0.4 saw only the library's
  overloads). A module that imports another module exporting a `toPgParam`
  with a built-in signature, such as `toPgParam*(v: string)`, now gets an
  ambiguous call for such values. Rename or drop that overload, or import the
  module with `except toPgParam` when you need none of its overloads.
- `toPgParam(seq[Option[T]])` and `get(row, col, seq[Option[T]])` exist for
  every `PgArray[T]` element type (0.4 had them for the integer, float, `bool`
  and `string` types only). A module that declares either for another element
  type, such as `toPgParam*(v: seq[Option[PgUuid]])`, now gets an ambiguous
  call. Drop that overload.
- `PgNumericSign` gains `pgInf` and `pgNegInf`, for numeric `Infinity` and
  `-Infinity` (PostgreSQL 14+), so a `case` over it without an `else` branch
  no longer compiles. Like `pgNaN`, they carry no digits.

## Behavior changes

- Under the default `rfAuto`, `json[]`, `name[]` and `bpchar[]`
  (`char(n)[]`) columns switch to binary once the same SQL text has already
  run on the connection (an earlier `exec` counts), as `text[]` and `jsonb[]`
  columns already did. From then on, `getStr` on such a column raises
  `PgTypeError` (0.4 returned the array text, such as `{pg_catalog,public}`
  for `current_schemas(true)`), and so does `getStrArray` on a `json[]`
  column. Read `name[]` and `bpchar[]` with `getStrArray`, `json[]` with
  `getJsonArray`, or pass `rfText`. The string helpers (`queryValue`,
  `queryColumn`, ...) read text and are unaffected.
- A `toPgParam` declared in the module that calls `pgParams` or `sql`, with a
  built-in signature such as `toPgParam(v: string)`, now encodes those values
  there instead of the library's overload, as it already did for direct
  `toPgParam(v)` calls in that module. Rename it to keep the library's
  encoding.
- `sqlParams` and `sql` put a space between the `$n` they write and an
  adjacent identifier, number or `$`, so `LIMIT?` binds the limit. 0.4 wrote
  `LIMIT$1`, which PostgreSQL reads as an identifier: in
  `SELECT * FROM generate_series(1, 5) LIMIT?` it became the table alias and
  every row came back. Code that compares the rewritten SQL sees the space,
  as in `$1 $2` for `{a}{b}`.
- A pool `acquire` that waited in the queue takes a slot once one frees
  under `maxSize`, then checks the idle connection that came with it (a
  health-check ping included) or dials for itself, within its own
  `acquireTimeout`, as an `acquire` that finds free capacity on arrival
  already did. It leaves the `pendingAcquires()` and `maxWaiters` count when
  it takes the slot, not when it gets a connection. 0.4 dialed in the
  background for the head of the queue, held that dial back during the
  connect backoff, and failed the most recently queued acquire when it
  failed. While the server is down, each queued acquire now dials once, with
  no backoff, and fails with `pekConnectFailed` instead of waiting out
  `acquireTimeout` for `pekAcquireTimeout`, and connects as soon as the
  server is back. A dial that outlasts the budget fails with
  `pekAcquireTimeout` and is abandoned (0.4 finished it and kept the
  connection for the next acquire). With `acquireTimeout = ZeroDuration` and
  no `connectTimeout`, nothing bounds that dial (0.4 bounded it by
  `maintenanceInterval`).
- `pool.close()` fails at once only the acquires still in the queue. An
  acquire that already got a slot and is dialing, or pinging an idle
  connection, ends when that dial or ping does: with `pekClosed`, or with the
  dial's own failure. `close()` without a timeout does not wait for it, and a
  connection it opens is closed (0.4 failed every queued acquire at once and
  waited for the background dial).
- An idle pool connection that received bytes while parked (a NOTIFY, or the
  FATAL a closing backend sends ahead of its FIN) is pinged before `acquire`
  hands it out, even with `healthCheckTimeout` or `tlsHealthCheckTimeout` at
  `ZeroDuration`, and the ping draws from `acquireTimeout`. With an empty
  `resetQuery`, a pooled connection that keeps a `LISTEN` thus costs a round
  trip on the first acquire after each NOTIFY, and its notifications are
  dispatched during that ping, or the maintenance sweep's, not during the next
  borrower's first operation.
- The maintenance sweep probes each idle connection. One the server closed is
  closed and replaced up to `minSize`, so with `minSize > 0` and a server-side
  `idle_session_timeout`, the pool reconnects each time the server drops its
  idle connections (0.4 counted them toward `minSize` until an acquire found
  them dead). One that received bytes is pinged, bounded by
  `maintenanceInterval` when `pingTimeout` is `ZeroDuration`, and counts
  toward `activeCount()` instead of `idleCount()` while the ping runs.
- A pool `withTransactionDeadline` or `withTransactionRetryDeadline` raises
  `PgTimeoutError` in fewer cases where the transaction commits, so a caller
  that retries on it no longer runs the transaction twice there:
  - Under asyncdispatch, when the deadline expires while the macro waits for
    `acquire`, the connection that acquire later delivers goes straight back
    to the pool, without running the body. 0.4 could still run the body and
    COMMIT on it after the caller had caught the `PgTimeoutError`.
  - When the deadline expires after COMMIT, while the pool resets the session
    (`resetQuery`, advisory locks, `TimeZone`), the macro returns normally.
    0.4 raised `PgTimeoutError` for the committed transaction.
- With `pipelined = true`, a dispatch that spreads its operations over
  several connections queues only for the first. It takes the rest while an
  idle connection or room under `maxSize` is free, and otherwise runs on
  fewer. The operations on one connection settle together when its pipeline
  ends, so on a busy pool more of them share each `timeout`
  (`maxPipelineSize` caps how many one dispatch takes). 0.4 queued for each
  one while holding those it had, so a dispatch that got some could wait for
  the rest on connections its own caller held, or concurrent dispatches on
  each other, until `acquireTimeout`, or for good with
  `acquireTimeout = ZeroDuration`. It still queues for the first, so a caller
  holding every connection waits on itself, as with `acquire`.
- Numeric `Infinity` and `-Infinity` (PostgreSQL 14+) decode in `getNumeric`,
  numeric arrays and ranges, and in `getStr` on a binary column, and
  `parsePgNumeric` accepts them. 0.4 raised `PgTypeError` for them everywhere
  but `getStr` on a text column, so under the default `rfAuto` the same query
  failed once it hit the statement cache. Code that takes any `sign` other
  than `pgNaN` for a finite value now also sees the infinities there; test
  the new `isFinite` instead.
