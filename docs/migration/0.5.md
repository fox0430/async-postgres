# Migrating from 0.4 to 0.5

This guide lists the changes since 0.4.1 that can break a build or change
runtime behavior.

## Compile errors

- `pgParams(v)` and `sql"…{v}…"` resolve `toPgParam` at the call site, as a
  direct `toPgParam(v)` call there does (0.4 saw only the library's
  overloads). A module that imports another module exporting a `toPgParam`
  with a built-in signature, such as `toPgParam*(v: string)`, now gets an
  ambiguous call for such values. Rename or drop that overload, or import the
  module with `except toPgParam` when you need none of its overloads.
- `toPgParam(seq[Option[T]])` and `get(row, col, seq[Option[T]])` exist for
  every `PgArray[T]` element type (0.4 had them for the integer, float, `bool`
  and `string` types only). A module that declares either for another element
  type, such as `toPgParam*(v: seq[Option[PgUuid]])`, now gets an ambiguous
  call. Drop that overload.
- `PgNumericSign` gains `pgInf` and `pgNegInf`, for numeric `Infinity` and
  `-Infinity` (PostgreSQL 14+), so a `case` over it without an `else` branch
  no longer compiles. Like `pgNaN`, they carry no digits.
- `PoolErrorKind` gains `pekAfterConnectFailed`, which `acquire` and
  `newPool` raise when the new `PoolConfig.afterConnect` hook fails, so a
  `case` over it without an `else` branch no longer compiles.
- `pgComposite(T)` also declares `get(row, col, typedesc[T])`, which reads
  with `getComposite`. A module that declares its own `get` for such a type
  now gets a redefinition or an ambiguous call. Drop yours, or, if it reads
  differently, keep it and declare `toPgParam` in place of `pgComposite`.

## Behavior changes

- Each connection returned to a pool is reset with the new default
  `resetQuery`, `DefaultResetQuery` (`CLOSE ALL; SET SESSION AUTHORIZATION
  DEFAULT; RESET ALL; UNLISTEN *; SELECT pg_catalog.pg_advisory_unlock_all();
  DISCARD TEMP; DISCARD SEQUENCES`), at the cost of a round trip per release.
  `SET`, `SET ROLE`, temporary tables, `LISTEN`, `WITH HOLD` cursors, session
  advisory locks and `currval` no longer reach the next borrower; startup
  parameters (`extraParams`) and prepared statements stay. 0.4 ran no reset
  unless `resetQuery` was set, and a `PoolConfig` built directly gets the new
  default too, bounded by a `resetQueryTimeout` of 5 s (0.4 left that
  field unbounded there). Set `resetQuery = ""` to keep the 0.4 behavior, and behind
  PgBouncer in transaction mode, RDS Proxy or Supavisor: RDS Proxy pins a
  session it sees `SET`, `RESET` or `DISCARD` on. A reset that fails closes
  the connection, as before, and now reaches the tracer's `onPoolCloseError`;
  with the new `afterConnect` hook set, the reset that follows the hook fails
  first and fails the connect (`pekAfterConnectFailed`).
- The reset runs in the background: the `with*` macros, `pool.exec`,
  `pool.query` and the other pool procs return without waiting for it, so a
  cancel or timeout cannot land on it after the operation succeeded, and a raw
  `release(conn)` or `release(h)` resets the session too. The connection keeps
  its slot until the reset ends, so `idleCount()` right after does not count
  it yet (`activeCount()` still does), and an `acquire` made meanwhile takes
  another idle connection or dials: code that borrows one connection at a
  time can open a second. 0.4 ran no reset on a raw release, and closed a
  connection holding typed-API advisory locks or a changed `TimeZone`; such a
  connection is now reset and kept. `pool.close()` cuts a reset still running
  short and closes its connection (asyncdispatch, which cannot cancel it,
  waits for it).
- A release puts back the callbacks a borrower set on the connection
  (`onNotice`, `onNotify`, `onNotifyOverflow`, `onListenError`, `onReconnect`)
  to what they were when the pool opened it (none, or what the new
  `afterConnect` hook set), and drops its
  channels and queued notifications, whatever `resetQuery` is. 0.4 left them,
  so the next borrower's notices reached the previous borrower's callback.
- Under the default `rfAuto`, `json[]`, `name[]` and `bpchar[]`
  (`char(n)[]`) columns switch to binary once the same SQL text has already
  run on the connection (an earlier `exec` counts), as `text[]` and `jsonb[]`
  columns already did. From then on, `getStr` on such a column raises
  `PgTypeError` (0.4 returned the array text, such as `{pg_catalog,public}`
  for `current_schemas(true)`), and so does `getStrArray` on a `json[]`
  column. Read `name[]` and `bpchar[]` with `getStrArray`, `json[]` with
  `getJsonArray`, or pass `rfText`. The string helpers (`queryValue`,
  `queryColumn`, ...) read text and are unaffected.
- A `toPgParam` declared in the module that calls `pgParams` or `sql`, with a
  built-in signature such as `toPgParam(v: string)`, now encodes those values
  there instead of the library's overload, as it already did for direct
  `toPgParam(v)` calls in that module. Rename it to keep the library's
  encoding.
- `sqlParams` and `sql` put a space between the `$n` they write and an
  adjacent identifier, number or `$`, so `LIMIT?` binds the limit. 0.4 wrote
  `LIMIT$1`, which PostgreSQL reads as an identifier: in
  `SELECT * FROM generate_series(1, 5) LIMIT?` it became the table alias and
  every row came back. Code that compares the rewritten SQL sees the space,
  as in `$1 $2` for `{a}{b}`.
- A pool `acquire` that waited in the queue takes a slot once one frees
  under `maxSize`, then checks the idle connection that came with it (a
  health-check ping included) or dials for itself, within its own
  `acquireTimeout`, as an `acquire` that finds free capacity on arrival
  already did. It leaves the `pendingAcquires()` and `maxWaiters` count when
  it takes the slot, not when it gets a connection. 0.4 dialed in the
  background for the head of the queue, held that dial back during the
  connect backoff, and failed the most recently queued acquire when it
  failed. While the server is down, each queued acquire now dials once, with
  no backoff, and fails with `pekConnectFailed` instead of waiting out
  `acquireTimeout` for `pekAcquireTimeout`, and connects as soon as the
  server is back. A dial that outlasts the budget fails with
  `pekAcquireTimeout` and is abandoned (0.4 finished it and kept the
  connection for the next acquire). With `acquireTimeout = ZeroDuration` and
  no `connectTimeout`, nothing bounds that dial (0.4 bounded it by
  `maintenanceInterval`).
- `pool.close()` fails at once only the acquires still in the queue. An
  acquire that already got a slot and is dialing, or pinging an idle
  connection, ends when that dial or ping does: with `pekClosed`, or with the
  dial's own failure. `close()` without a timeout does not wait for it, and a
  connection it opens is closed (0.4 failed every queued acquire at once and
  waited for the background dial).
- An idle pool connection that received bytes while parked (a NOTIFY, or the
  FATAL a closing backend sends ahead of its FIN) is pinged before `acquire`
  hands it out, even with `healthCheckTimeout` or `tlsHealthCheckTimeout` at
  `ZeroDuration`, and the ping draws from `acquireTimeout`. With an empty
  `resetQuery`, a pooled connection that keeps a `LISTEN` thus costs a round
  trip on the first acquire after each NOTIFY, and its notifications are
  dispatched during that ping, or the maintenance sweep's, not during the next
  borrower's first operation.
- The maintenance sweep probes each idle connection. One the server closed is
  closed and replaced up to `minSize`, so with `minSize > 0` and a server-side
  `idle_session_timeout`, the pool reconnects each time the server drops its
  idle connections (0.4 counted them toward `minSize` until an acquire found
  them dead). One that received bytes is pinged, bounded by
  `maintenanceInterval` when `pingTimeout` is `ZeroDuration`, and counts
  toward `activeCount()` instead of `idleCount()` while the ping runs.
- A pool `withTransactionDeadline` or `withTransactionRetryDeadline` raises
  `PgTimeoutError` in fewer cases where the transaction commits, so a caller
  that retries on it no longer runs the transaction twice there:
  - Under asyncdispatch, when the deadline expires while the macro waits for
    `acquire`, the connection that acquire later delivers goes straight back
    to the pool, without running the body. 0.4 could still run the body and
    COMMIT on it after the caller had caught the `PgTimeoutError`.
  - When the deadline expires after COMMIT, while the pool resets the session
    (`resetQuery`, advisory locks, `TimeZone`), the macro returns normally.
    0.4 raised `PgTimeoutError` for the committed transaction.
- With `pipelined = true`, a dispatch that spreads its operations over
  several connections queues only for the first. It takes the rest while an
  idle connection or room under `maxSize` is free, and otherwise runs on
  fewer. The operations on one connection settle together when its pipeline
  ends, so on a busy pool more of them share each `timeout`
  (`maxPipelineSize` caps how many one dispatch takes). 0.4 queued for each
  one while holding those it had, so a dispatch that got some could wait for
  the rest on connections its own caller held, or concurrent dispatches on
  each other, until `acquireTimeout`, or for good with
  `acquireTimeout = ZeroDuration`. It still queues for the first, so a caller
  holding every connection waits on itself, as with `acquire`.
- Cancelling (chronos) `conn.withTransaction*` or `conn.withSavepoint*`
  while its body awaits something other than a round trip retires the
  connection (`csClosed`). The socket stays open until `await conn.close()`,
  as after a timeout. 0.4 left the connection usable inside the transaction
  or savepoint: the caller's next statements ran in the abandoned
  transaction, and a caller that caught a cancelled `withSavepoint*` (a
  `wait` timeout, say) and went on had the savepoint's writes committed with
  the enclosing transaction, on a pooled connection too. A cancelled
  `withSavepoint*` now ends the enclosing transaction. An expired deadline of
  an enclosing `conn.with*Deadline` macro still rolls back and keeps the
  connection. The pool's `withTransaction*` macros leave the connection
  `csClosed` too; release already discarded one left in a transaction.
- A `withTransaction*` body (conn, pool and cluster) that ends its own
  transaction with `COMMIT`, `ROLLBACK`, `END`, `ABORT` or
  `PREPARE TRANSACTION` raises `PgStateError` in place of the macro's COMMIT,
  which is no longer sent. The connection stays usable, and the retry macros
  do not retry the error. 0.4 sent COMMIT, which the server answered with a
  "there is no transaction in progress" warning, and returned normally. To
  abort from inside the body, raise instead, and the macro rolls back. For
  two-phase commit, send `BEGIN` and `PREPARE TRANSACTION` yourself with
  `exec`: the transaction a body prepared outlives the error and holds its
  locks until `COMMIT PREPARED` or `ROLLBACK PREPARED`.
- Numeric `Infinity` and `-Infinity` (PostgreSQL 14+) decode in `getNumeric`,
  numeric arrays and ranges, and in `getStr` on a binary column, and
  `parsePgNumeric` accepts them. 0.4 raised `PgTypeError` for them everywhere
  but `getStr` on a text column, so under the default `rfAuto` the same query
  failed once it hit the statement cache. Code that takes any `sign` other
  than `pgNaN` for a finite value now also sees the infinities there; test
  the new `isFinite` instead.
- `to(row, T)` and `to(qr, seq[T])` read rows into an object, a `ref object`
  or a tuple. A module that declares its own generic
  `to[T](row: Row, _: typedesc[T])` or `to[T](qr: QueryResult, _: typedesc[seq[T]])`
  now calls the library's for those types instead, with no compile error:
  the library's constrains `T`, which makes it the closer match. Rename yours
  to keep it. An overload for one type, such as
  `to(row: Row, _: typedesc[User])`, still wins.
- `getDomain` and `getDomainOpt` read a distinct type as `to` reads a field
  of it: with a `get` overload you declare for the distinct type, else as its
  base type. A `DateTime` base follows the column's type, so a timestamptz or
  date domain reads; 0.4 always read a timestamp, which raised `PgTypeError`
  on a date column and, once the statement was cached under the default
  `rfAuto`, on a timestamptz column. Any base type `to` reads now compiles
  (0.4 took eight). A `get` you declare for the distinct type that calls
  `getDomain` for that type now calls itself until the stack overflows; read
  the base type there with its accessor, as in `Zip(row.getStr(col))`.
- `toPgRangeParam` and `toPgMultirangeParam` write `DateTime` bounds, and
  those of a `distinct DateTime` such as a domain's type, in UTC, as
  `toPgParam`, `toPgTsTzRangeParam` and `toPgDateRangeParam` do. 0.4
  wrote the value's own wall clock, so a tsrange or daterange (or a range
  type of your own over timestamp or date) built from a `DateTime` outside
  UTC was stored off by its offset, as a different hour or day; tstzrange was
  right. For the built-in range types each bound gets the range check of a
  lone value, so one PostgreSQL cannot store raises `PgTypeError`; a
  `toPgRangeParam` call over `DateTime` bounds can now raise it, while other
  element types raise as before. A range type of your own gets only the date
  window checked, and the server rejects a bound its subtype cannot hold.
  `$` of such a range still shows the local wall clock.
- The `toPgParam` that `pgComposite` declares writes a `distinct DateTime`
  field, and the bounds of a `PgRange` or `PgMultirange` field over
  `DateTime` or a `distinct DateTime` (or a `distinct` type over such a
  range or multirange, or an `Option` of any of these), as UTC instants, as
  it writes a `DateTime` field. 0.4 wrote `$` of the value,
  so a timestamp, date, tsrange, daterange or tsmultirange attribute was
  stored off by the value's offset. The distinct type no longer needs a `$`.
- `parseDsn` (and so `connect(dsn)` and `connectReplication(dsn)`) fills in
  what the string leaves out as libpq does: from the `service` named there
  (or by `PGSERVICE`) in the connection service file, else from libpq's
  environment variables (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`,
  `PGPASSWORD`, `PGSSLMODE`, ...). An empty user becomes the OS
  user, and with no password the new `ConnConfig.passFile`, `~/.pgpass` by
  default, is read for each host at connect. On a machine where
  `PGDATABASE` or `PGSSLMODE` is set, a DSN without `dbname` or `sslmode`
  now uses it; 0.4 used the user name as the database and `prefer`.
  `PGTZ` is not read, unlike libpq: it would move the session `TimeZone`, and
  a `DateTime` parameter bound to `timestamptz` shifts by that zone's offset
  (0.4's `TimeZone` is UTC). Set `TimeZone` in the DSN, `options` or
  `extraParams` to change it. A `PGOPTIONS` with `-c client_encoding=` (not
  UTF8) or `-c DateStyle=` (not ISO) is a `PgConfigError`, as that switch in
  the string is; 0.4 ignored `PGOPTIONS`. An `sslrootcert` that exists with
  `sslmode=require` is a `PgConfigError` whether it came from the string, a
  variable or the service file: libpq verifies the server against it under
  `require`, which this client would not, so the connection would accept any
  certificate. Use `sslmode=verify-ca`.
  `parseDsn(dsn, environment = false)` keeps 0.4's defaults: no `PG*`
  variable, no default file and no OS user. A `passfile` in the string is
  still read (0.4 sent it to the server, which refused it), while a
  `service` in the string has no file to search and raises. Otherwise
  `service` and `passfile` are resolved here rather than sent to the server:
  0.4 sent both, which refused them, so a DSN containing either failed to
  connect.
  Combined with a `credentialsProvider`, a password from `PGPASSWORD` is the
  same `PgConfigError` as a DSN's: clear `password` after `parseDsn`. An
  empty `PG*` variable counts as unset: `PGSSLMODE=` keeps `prefer`,
  `PGSERVICE=` is ignored, and `PGSERVICEFILE=` falls back to the user's
  `~/.pg_service.conf`. libpq instead stores the empty value, so an empty
  `PGSSLMODE` (an enum) is an error there.
- A libpq keyword this client does not implement, in a DSN, a variable or
  the service file, is ignored (`gssencmode=disable`, `krbsrvname`, ...),
  or raises `PgConfigError` if it asks
  for a check or a limit this client would not apply (`sslcrl`,
  `requirepeer`, `sslcertmode=require`,
  `ssl_min_protocol_version=TLSv1.3`, ...). 0.4 sent such a keyword in a DSN
  to the server as a startup parameter, which it refused, so a DSN holding
  one failed to connect. `ssl_max_protocol_version=TLSv1.2` is refused only
  on asyncdispatch, which may negotiate TLS 1.3; chronos speaks TLS 1.2 only.
- `tcp_user_timeout` is a client setting now, as in libpq: it goes to the new
  `ConnConfig.tcpUserTimeout` and is set on the socket on Linux for a TCP
  host with keepalives on, and ignored elsewhere. PostgreSQL 12+ has a server
  setting of the same name, which 0.4 set by sending the keyword as a startup
  parameter; use `options=-c tcp_user_timeout=30000` to keep that. A `0` in
  a DSN no longer resets a `tcp_user_timeout` the server sets globally.
- `sslsni` is on only for a value starting with `1`, as in libpq (`sslsni=2`
  or `-1` turned it on in 0.4).
- `fallback_application_name` sets `application_name` when none is set, as
  in libpq.
- `sslcertmode=disable` is honored, not ignored: no client certificate is
  sent, and an `sslcert`/`sslkey` taken from a variable or the service file
  is left unread. A `sslcert` in the DSN with it raises `PgConfigError`
  unless `sslmode` is `disable` or `allow`, where it and `sslkey` are dropped
  unread; so is a DSN `sslkey` given without `sslcert`, in any mode.
- The deprecated `requiressl` is read as `sslmode`, as libpq reads it in a
  DSN or URI: a value starting with `1` is `require`, anything else
  `prefer`. In the service file it raises `PgConfigError`, as libpq rejects
  it there. A URI's `ssl=true` is read as `sslmode=require`. 0.4 sent both to the server
  as startup parameters, which refused them.
- A key set twice in a DSN keeps the last value, as in libpq (a startup
  parameter's name is matched without case, as the server does, but a
  keyword only in its own case). 0.4 applied each in turn, so an invalid
  earlier value (`sslmode=bogus sslmode=require`) raised.
- Integer keywords take surrounding spaces and a sign, as libpq does
  (`connect_timeout=' 5'`), and a libpq keyword's value must fit a C int:
  `connect_timeout` above 2147483647 now raises `PgConfigError`.
